0. Review Findings — Draft 0.1 → 0.2

Overall verdict: the architecture is sound and the principles (immutable facts, definitions-as-data, fail-open, portable-first, host-owned policy) are the right ones. 1. Product Definition

This is a first-party analytics platform for private business applications and public websites. It captures product usage, acquisition, conversions, identity, sessions, presence, and safe application context without making a third-party analytics service the system of record.

Core principle: events are immutable facts. Features, funnels, conversions, cohorts, attribution, and dashboards are interpretations of those facts.

Primary use cases

  • Private apps: login frequency, current activity, route/page usage, Livewire actions, feature adoption, retention, and user journeys.
  • Public sites: anonymous sessions, landing pages, referrers, UTMs, click identifiers, campaigns, funnels, conversions, and revenue.
  • Mixed apps: preserve acquisition history as an anonymous visitor becomes an authenticated user.
  • Operational correlation: connect an analytics event to the request, trace, log stream, or queued job that produced it.

Non-goals

Do not rebuild Datadog, Sentry, OpenTelemetry, Elasticsearch, or a data warehouse. Integrate with those systems through correlation IDs and export hooks. Analytics answers what users and the business did; observability answers what the software did and why it failed.

2. Monorepo & Package Boundaries

analytics/
├── packages/
│   ├── core/          # event pipeline, identity, sessions, context, contracts
│   ├── product/       # adoption, retention, cohorts, feature semantics
│   ├── marketing/     # campaigns, conversions, attribution, funnels, revenue
│   ├── filament/      # Filament 5 UI
│   ├── timescale/     # optional PostgreSQL/Timescale acceleration
│   └── destinations/  # outbound conversion/export adapters
├── workbench/         # real Laravel demo/test application
├── tests/
├── docs/
├── composer.json
└── README.md

Each package is independently installable and follows Spatie-style Laravel package conventions. Use spatie/laravel-package-tools where it removes boilerplate. The root repository owns CI, code style, static analysis, shared test tooling, documentation, and release orchestration.

Dependency direction: core knows nothing about Filament, Timescale, marketing semantics, or external destinations. Higher layers depend inward.

Packages are developed in the monorepo via Composer path repositories and split to read-only per-package repositories on tag (symplify/monorepo-builder or a splitsh GitHub Action). All packages are versioned in lockstep so core ^1.3 always pairs with filament ^1.3. The workbench/ directory follows Orchestra Testbench's Workbench convention so the demo app doubles as the integration-test host.

4. Event Model

The raw event table is append-only. An event describes something that happened and is not mutated later to make a report easier.

{
  "id": "01J...",
  "occurred_at": "2026-09-29T14:20:12.123Z",
  "received_at": "2026-09-29T14:20:12.191Z",
  "name": "report.exported",
  "version": 1,
  "actor_type": "App\\Models\\User",
  "actor_id": "742",
  "anonymous_id": "anon_...",
  "session_id": "sess_...",
  "tenant_type": "App\\Models\\Company",
  "tenant_id": "42",
  "request_id": "req_...",
  "trace_id": "trace_...",
  "parent_id": null,
  "dedupe_key": "req_..:Reports\\Show:export:1",
  "source": "livewire",
  "environment": "production",
  "properties": {"format":"xlsx","report":"sales-summary"},
  "context": {"route":"reports.show","component":"Reports\\Show"}
}
The campaign block was removed from the per-event envelope. Acquisition data is stored once per session/touchpoint row (§10) and joined via session_id; repeating it on every event bloats the largest table for no query benefit. dedupe_key was added so at-least-once transports (queue retries, redis-buffer replays, client beacon resends) can be made idempotent at insert time with a unique index; it is deterministic (request + component + action + ordinal, or a client-supplied ULID). environment was added so staging traffic can never pollute production reports.
  • Use sortable UUID/ULID identifiers; timestamps are UTC with sub-second precision. Store as timestamptz on PostgreSQL and DATETIME(6) (not TIMESTAMP, which ends in 2038) on MySQL; store ULIDs as CHAR(26) or BINARY(16) consistently and document the choice because it affects index size at year two.
  • Reject occurred_at more than a configurable skew into the future; clamp or flag events far in the past; always trust received_at for ordering guarantees.
  • Bound event names, property depth/count, and payload size.
  • Never automatically capture request bodies, passwords, tokens, arbitrary headers, form values, or model snapshots.
  • JSON properties provide flexibility; frequently queried dimensions may be promoted to indexed columns.
  • Version event semantics so later changes do not silently reinterpret history.
  • Immutability, precisely: events are never mutated to make a report easier. The single sanctioned mutation is privacy erasure (§12), which rewrites actor columns to a tombstone in batches and marks affected rollups for rebuild.

5. Collection Strategy

HTTP middleware

At request entry establish request/session/actor/tenant/campaign context, update presence, and optionally record route/page observations. Prefer named routes over raw URLs so IDs and sensitive path segments do not explode cardinality; for unnamed routes fall back to the route URI pattern (users/{user}), never the resolved path.

Page-view capture happens in middleware, but the event is buffered in memory and flushed after the response is sent (terminable middleware / dispatchAfterResponse), so collection never adds latency to the user's request. Distinguish wire:navigate fetches (header X-Livewire-Navigate) from full loads: they are real page views, but prefetch-on-hover requests are not.

Client beacon (public sites)

Server-only capture is insufficient for public marketing sites: full-page and CDN caching mean the middleware never runs for cached hits, and bots dominate what it does see. Ship a small, dependency-free first-party script (a few hundred bytes, navigator.sendBeacon to a package-provided /collect route) that reports page views, outbound clicks and optional engagement time. The server remains the source of truth: it validates payloads against the same limits as any event, resolves identity from the first-party cookie (or the session in cookieless mode), applies the same TrackingDecision hook, and dedupes on dedupe_key. The beacon is optional and off by default for private apps, where server-side capture is complete.

Authentication

Subscribe to Laravel authentication events for login/logout and identity transitions. Do not infer authentication from URLs.

Map events deliberately: Login → auth.login; Registered → auth.registered (also the identity-merge trigger); Logout, CurrentDeviceLogout, OtherDeviceLogout → auth.logout with a reason; Failed/Lockout → opt-in security facts. Do not record Authenticated, which fires on every request for session guards and would inflate login frequency, and do not treat "remember me" cookie logins as a new login unless configured.

Livewire 4

Corrected: Livewire 4's interceptAction, interceptMessage and interceptRequest are JavaScript interceptors. They run in the browser and cannot be trusted for analytics. Server-side capture uses Livewire's PHP ComponentHook lifecycle (registered once from the service provider): the call hook sees every action with its component and method name; hydrate/dehydrate bracket the request. Record component class + action name by default, never method parameters. Exclude non-intent traffic: wire:poll ticks, lazy/island loads, wire:model.live property syncs with no action, and file-upload chunking. When one /livewire/update request carries several components or several queued actions, each action is its own event sharing one request_id. The JS interceptors may optionally be used later for client-side timing (perceived latency), never for facts.

Explicit business events

Analytics::track('quote.accepted', [
    'quote_type' => 'commercial',
    'value' => 12500,
]);

Automatic tracking answers “what UI capability was invoked.” Explicit events answer “what business fact occurred.” Both belong in the same pipeline.

6. Request, Trace & Queue Correlation

Create or adopt a correlation context at request entry: request ID, trace ID, actor, tenant, anonymous/session identity, campaign snapshot, and optional parent event ID. If OpenTelemetry already exists, adopt its trace/span IDs rather than creating a competing tracing standard.

Build on Laravel's Illuminate\Support\Facades\Context rather than a bespoke envelope. It already propagates to queued jobs (including chains and batches), exposes dehydrating/hydrated hooks for anything that needs custom serialization, supports hidden keys for values that must not reach logs, and is automatically merged into log context — which is what §18 asks for. The package's contribution is the set of keys, the resolvers that populate them, and the hooks that keep them minimal (IDs only, never model instances). Commands and scheduled work get a synthetic root context with no actor.
Long-lived process safety: context must be explicitly cleared after each request/job — this covers queue workers, Horizon, and Octane (Swoole/FrankenPHP/RoadRunner) app workers alike. A worker must never leak the previous user's identity or campaign into the next request or job. The package registers itself with Octane's request-terminated and Laravel's job-processed events to flush and reset.

7. Ingestion & Failure Model

DriverUse
syncTests/local/tiny deployments.
queueSafe production default using Laravel queues.
redis-bufferHigh-volume compact buffer followed by batch database inserts.
nullExplicitly disable analytics.
All drivers sit behind a per-request buffer: events collected during a request (or job) are held in memory and handed to the transport after the response is sent. The queue driver dispatches one job per request carrying all of that request's events, not one job per event; on Octane the buffer is flushed and reset per request, not per process. The /collect beacon endpoint writes through the same buffer.

Batch inserts are preferred. Analytics is fail-open: if analytics is unavailable, the application's primary business operation still succeeds. Provide bounded buffering, retry policies, dead-letter visibility, dedupe IDs, and backpressure limits.

Establish performance budgets for middleware overhead, envelope size, queue lag, batch flush latency, and dropped-event rate.

8. Presence

Presence is ephemeral and separate from durable analytics. “Online” means recently active, not “has a session row.” Refresh an expiring Redis/cache key on meaningful authenticated activity. Make TTL configurable (for example five minutes) and rate-limit refreshes.

Expose current count, authorized identity list, last seen, and tenant-scoped presence. Presence may degrade without breaking event collection or the host app.

9. Identity Resolution

Anonymous visitors receive first-party anonymous and session IDs. On authentication/registration, explicitly link anonymous identity to the known actor. Never fingerprint or infer identity from IP/user agent.

Merges must be auditable. Tenant membership is context, not identity. Support configurable actor and tenant resolvers instead of assuming a particular User/Team model.

Merge semantics: an alias links an anonymous ID to exactly one actor, with an effective time range. If the same anonymous ID later authenticates as a different actor (shared device, kiosk), open a new range rather than re-pointing history — never merge two actors. Only events inside a range are attributed to that actor; an anonymous ID with no alias stays anonymous forever.

Sessions

Sessions were used throughout Draft 0.1 but never defined. An analytics session is: a first-party session_id (ULID) held alongside, but separate from, the Laravel session — Laravel regenerates its ID on login and logout, and that must not split an analytics session. A session ends after a configurable inactivity gap (default 30 minutes) or a hard cap (default 24 hours); a new arrival with new campaign parameters starts a new session so acquisition is attributed correctly. Session rows hold: started/ended, actor at end, anonymous ID, landing route, referrer, acquisition snapshot (§10), event count, and last-seen. Sessions are the unit for "sessions per user", bounce, and touchpoints. In cookieless mode (§12) the session is bound to the Laravel session lifetime and there is no cross-session anonymous identity.

10. Marketing Analytics

Acquisition

Capture landing page, referrer, UTM source/medium/campaign/content/term, and configured ad click IDs. Preserve original/first-touch and current/session acquisition context.

Conversions are definitions over facts

Conversion "Consulting Lead"
  event: lead.created
  where: properties.service == "consulting"

Conversion "Purchase"
  event: order.completed
  value: properties.revenue

Definitions live in data and can be managed in Filament. Because raw facts already exist, a conversion can be created later and evaluated historically. Code-defined definitions may also be supported for teams that want version control.

Click IDs (gclid, fbclid, msclkid, ttclid…) are identifiers, not campaign labels: store them only when the host has enabled the corresponding destination or opted in, subject to the same retention and consent rules as the anonymous ID. Revenue values carry a currency and are stored in minor units (integer) to avoid float drift in rollups.

Attribution

Compute attribution at query/report time. Ship first-touch and last-touch first; leave room for linear/position-based models. Always display the model used.

Attribution is computed over a compact touchpoint table — one row per session with acquisition data (source/medium/campaign/content/term, referrer class, landing route, click-ID presence, actor/anonymous ID, timestamp) — not over raw events. This keeps query-time attribution viable at year two and lets it be evaluated for any conversion definition retroactively. Every model takes a configurable lookback window (default 90 days) and the model + window are stamped on every report. Touchpoints are derived data and rebuildable from session rows.

Destinations

Later, normalized conversions can be forwarded server-side to ad/CRM destinations. Vendor adapters consume conversions; they do not reshape the core event model.

11. Product Analytics

Build DAU/WAU/MAU, login frequency, feature adoption, frequency, new/returning behavior, journeys, retention, cohorts and funnels over the same events.

Features are definitions. “Reporting” might consist of selected routes, selected Livewire actions, and report.exported. Funnels are ordered predicates with a time window. Cohorts are saved predicates over actor attributes and behavior. Both support historical evaluation.

Uniques are a separate derived layer. DAU/WAU/MAU, "unique users who used feature X this month", retention and cohort sizes are distinct counts, and distinct counts cannot be summed from hourly or daily rollups (a user active in 30 hourly buckets is one user, not 30). Maintain an actor-activity table keyed (tenant, actor, date, [feature|event]) with one row per actor-day; it is small (bounded by users × days, not events), portable to MySQL, and answers every uniques question with a COUNT(DISTINCT) over a date range. Rollups (§14) carry event counts, sums and durations; activity tables carry uniques. Dashboards must never compute uniques from rollups. HyperLogLog sketches are a later, Postgres-only optimization behind the Timescale/extension adapter.

12. Filtering, Privacy & Escape Hatches

Do not assume employees/internal users should be excluded. In private apps, they may be the main audience. Instead expose a composable decision hook:

interface TrackingDecision
{
    public function decide(AnalyticsContext $context): Decision;
}

A host app can track, drop, sample, redact, or tag. Built-ins may recognize bots, health checks, routes, users, IP ranges, user agents, environments and tenants, but policy belongs to the host application.

Provide property allow/block lists, optional IP omission/anonymization, retention policies, actor erasure/anonymization, consent-state hooks, and export APIs. Sensitive payload capture is opt-in.

Defaults that keep a host out of trouble: IP addresses are not stored by default (an optional truncated/hashed form for bot and abuse filtering is opt-in). The package ships in cookieless mode: no persistent visitor cookie, anonymous identity lives for the Laravel session only. The persistent first-party anonymous cookie (which enables returning-visitor and cross-session attribution) is opt-in per host and gated behind the consent-state hook, because a first-party analytics cookie set before consent is still an ePrivacy issue in the EU. Erasure is implemented as a queued, chunked job that rewrites actor_id/anonymous_id to a tombstone value, deletes alias and session rows for the actor, strips configured PII properties, and queues rollup rebuilds for the affected buckets; it is the only write path that touches existing events and is audited.

13. PostgreSQL, MySQL & Timescale

Portable baseline

All semantic features work on ordinary PostgreSQL and MySQL using append-only events, disciplined indexes, rollup tables, bounded JSON, batch ingestion, and background aggregation.

All package tables live on a configurable database connection (default: the app's), so the analytics store can be moved to its own database without code changes; migrations, queries and the Filament plugin honor that connection. The event and rollup tables carry no foreign keys — MySQL partitioned tables cannot have them, and the store must tolerate deleted users/tenants anyway. On MySQL, promoted JSON dimensions use generated columns with indexes; on PostgreSQL, jsonb with expression indexes. The same behavior suite proves both.

Partitioning

Partitioning is an optimization layer. PostgreSQL and MySQL have different operational behavior; keep database-specific strategies behind storage/maintenance adapters instead of pretending the SQL is identical.

Timescale adapter

The optional package can configure event storage as a hypertable and use capabilities detected on the installed Timescale edition. Never assume compression, tiering, continuous aggregates, or other edition/provider-specific features exist.

Neon: keep Timescale optional. Neon can expose TimescaleDB, but hosted feature availability can differ from full Timescale Cloud/self-hosted capabilities. The package's portable rollup system remains the compatibility baseline.

14. “Year Two” Architecture

Analytics systems tend to fail because they succeed: the event table becomes enormous and dashboards accidentally query raw history. Design for two years of operation from day one.

  • Dashboards query hourly/daily rollups for counts and the actor-activity table for uniques (§11), not the raw event firehose.
  • Raw events remain factual truth for the configured retention period.
  • Rollups are rebuildable and versioned so calculation bugs can be corrected.
  • Aggregation jobs use checkpoints/watermarks and are idempotent.
  • Late-arriving events reopen/recompute affected buckets.
  • Cardinality guards detect exploding event names and property values.
  • Retention can keep recent raw data hot, export/archive older data, then prune it.
  • Large-table migrations avoid full-table rewrites and long blocking locks.
  • Backfills are chunked, resumable, observable, and safe to pause.

Self-health

Track event rate, table/index growth, aggregation lag, queue lag, rejected/dropped events, batch size, query latency, cardinality warnings, and projected retention footprint.

Support multiple Filament panels, authorization/policies, tenant scoping, configurable navigation, host-app overrides, configurable widgets, and custom dashboard composition. Expensive widgets use rollups/cache rather than polling raw events.

Filament widgets default to polling; analytics widgets ship with polling off and a manual refresh, since the underlying data is minutes-fresh by design.

16. Developer API & Extension Points

// Explicit business fact
Analytics::track('invoice.paid', [
    'amount' => 2500,
    'currency' => 'USD',
]);

// Scoped safe context
Analytics::withContext(['workflow' => 'renewal'], function () {
    // events inherit context
});

Analytics::identify($user);
Analytics::alias($anonymousId, $user);

// Feature definitions live under the same facade (see note)
Analytics::feature('reporting')
    ->events(['report.viewed', 'report.exported'])
    ->routes(['reports.*']);
Naming collisions. Draft 0.1 used Feature::define('reporting'), which is exactly Laravel Pennant's facade and signature — a host using Pennant for feature flags would have two Feature facades. Feature definitions now hang off the analytics facade. The Analytics facade itself is also a problem: spatie/laravel-analytics (Google Analytics) registers an Analytics alias, and it is common in exactly the marketing sites this package targets. Analytics:: is a placeholder in this document; the real facade and namespace are named after the product (open question 1, §20) and must not shadow Pennant, Spatie, or Laravel's own Context.

Expose contracts for actor resolution, tenant resolution, context enrichment, redaction, tracking decisions, ingestion transport, storage, aggregation, presence, attribution, conversion evaluation, and export.

Configuration philosophy

Infrastructure choices belong in code/config: queue, storage, resolvers, privacy hooks, hard limits. Business analytics concepts belong in data/UI: conversions, funnels, cohorts, feature definitions, attribution/report settings. Definitions should support JSON import/export for optional version control.

17. Testing Strategy — Including Real-World Failure Modes

Unit tests

  • Event normalization and schema validation.
  • Context merging/clearing and property redaction.
  • Conversion predicate evaluation and attribution algorithms.
  • Feature/funnel/cohort predicates.
  • Identity alias/merge behavior and retention calculations.

Database contract tests

Run the same behavior suite against real PostgreSQL and real MySQL in CI. SQLite is not sufficient as the primary database test because JSON, indexing, timestamp, locking, query planner and migration behavior differ.

Laravel integration tests

  • HTTP middleware + authentication lifecycle.
  • Named route capture and excluded route behavior.
  • Queue context propagation across jobs, chains and batches.
  • Failed/retried jobs do not duplicate events unless semantics require it.
  • Horizon/long-lived workers do not leak context.
  • Octane (Swoole and FrankenPHP) request isolation: two sequential requests from different users never share buffer or context.
  • Analytics session survives Laravel session regeneration on login/logout.
  • Cookieless mode stores nothing persistent; consent hook flipping mid-session behaves as documented.
  • Beacon endpoint: rejects oversized/malformed payloads, dedupes resends, applies TrackingDecision.

Livewire 4 tests

  • Server-side ComponentHook records intended component/action metadata; polls, lazy loads and property syncs are excluded.
  • High-frequency updates do not become accidental high-cardinality analytics.
  • Action parameters are not captured by default.
  • Bundled/multiple actions remain distinguishable.

Filament 5 tests

  • Plugin registration across multiple panels.
  • Authorization and tenant scoping on every resource/widget/page.
  • Definition builders serialize valid predicates.
  • Dashboard queries hit rollups where intended.

Failure injection

  • Redis unavailable.
  • Analytics DB unavailable.
  • Queue paused/backlogged.
  • Duplicate delivery.
  • Partial batch insert failure.
  • Clock skew and late events.
  • Malformed/oversized properties.
  • Worker crash between dequeue and persistence.

Correctness of derived data

Property-style tests that recompute DAU/WAU/MAU, feature uniques, funnel completion and retention directly from raw events on a generated dataset and assert the rollup/activity-table answers match exactly. This is the test that catches "summed uniques" and late-event bugs, and it runs on every change to aggregation code.

Load & aging tests

Generate realistic synthetic data representing at least two years: many tenants, users, sessions, skewed “hot” features, marketing campaigns, anonymous-to-known transitions, and bursty Livewire traffic. Measure ingestion throughput, p95/p99 request overhead, rollup lag, dashboard latency, index/table size, retention/pruning duration, and backfill duration.

Migration tests

Keep snapshots representing old package versions with large tables. Upgrade them in CI/staging-like tests. Verify migrations are resumable and avoid dangerous locks/full rewrites. A package that only tests fresh installs is not sufficiently tested.

Privacy/security tests

Use canary secrets and PII-like values to verify that passwords, authorization headers, CSRF tokens, arbitrary form payloads, and blocked properties never enter stored events. Test tenant isolation as a security boundary.

18. Operability & Diagnostics

Ship an Artisan diagnostic command and Filament Health page. The command should validate migrations, queue configuration, storage connectivity, Redis/presence availability, aggregation freshness, extension capabilities, event growth, indexes, retention configuration and unsafe cardinality.

php artisan analytics:doctor
php artisan analytics:aggregate
php artisan analytics:backfill --from=...
php artisan analytics:prune
php artisan analytics:rebuild-rollups
php artisan analytics:inspect event.name

Emit Laravel events for ingestion failures and health thresholds so host applications can route alerts however they choose. Do not hard-wire an alert vendor.

Observability integration

Add analytics context to Laravel's logging context when configured, and accept external trace IDs. Provide a small API to generate links/pivots from an analytics event to an application's observability tooling without copying log payloads into analytics.

19. Suggested Delivery Plan

Capture before reporting. Anything that cannot be back-filled — sessions, anonymous identity, acquisition (UTMs, referrer, landing page, first-touch), auth facts — is captured from Phase 1, even though the reports that use it arrive in Phases 3 and 5. A Phase 1 install that skips these loses that history permanently.

Phase 1 — Core facts & capture

Monorepo skeleton; event schema with dedupe keys; Laravel Context integration; actor/tenant resolvers; HTTP/auth collection with after-response buffering; session lifecycle, anonymous identity (cookieless + opt-in cookie), acquisition capture into session/touchpoint rows; sync + queue transports; PostgreSQL/MySQL; privacy limits and erasure; basic CLI; package contract tests.

Phase 2 — Livewire, presence & runtime hardening

Livewire 4 ComponentHook capture with noise exclusion, Redis/cache presence, queue/Octane propagation and isolation, fail-open behavior, optional client beacon, and performance baselines.

Phase 3 — Product analytics

Feature definitions, rollups and actor-activity tables, DAU/WAU/MAU, user activity, adoption, funnels, cohorts, retention, historical evaluation, and the derived-data correctness suite.

Phase 4 — Filament 5

Overview, users, features, events, funnels, retention and Health. Establish plugin configuration/authorization/tenant contracts before marketing UI.

Phase 5 — Marketing reporting

Conversion definitions, revenue, first/last attribution over touchpoints, campaign reporting, click-ID capture (opt-in), anonymous-to-known conversion paths. (Raw acquisition capture already exists from Phase 1.)

Phase 6 — Scale adapters

Optional Redis buffering, native partition strategies, Timescale capability adapter, retention/archive/export, large-instance migration tooling.

Phase 7 — Destinations

Server-side conversion destination contracts and initial adapters only after internal conversion semantics are stable.

20. Architectural Decisions to Freeze Before Implementation

  1. Event immutability: raw facts are append-only.
  2. Explicit meaning: automatic capture supplies baseline behavior; important business facts use explicit events.
  3. Definitions as data: features, funnels, cohorts and conversions can be created after events exist.
  4. Analytics is not logging: share correlation IDs; keep storage/purpose separate.
  5. Fail-open: analytics failure never blocks core business behavior.
  6. Portable first: PostgreSQL and MySQL are complete products; Timescale is an optimization.
  7. No implicit PII: collection is conservative and bounded.
  8. No guessed identity: anonymous-to-known linkage is explicit.
  9. Rollups are disposable: derived data can be rebuilt from retained facts.
  10. Year-two performance is a release requirement: aging/load/migration tests are part of CI/release qualification.
  11. Filament is presentation: core remains usable without Filament.
  12. Host app owns tracking policy: filtering is hookable rather than opinionated around “internal” users.
  13. Uniques never come from rollups: distinct-user metrics are computed from the actor-activity layer.
  14. Capture precedes reporting: non-backfillable facts (sessions, anonymous identity, acquisition) ship in Phase 1.
  15. Build on Laravel primitives: Context for propagation, auth events for identity, after-response hooks for buffering — no parallel infrastructure.
  16. Privacy-safe by default: cookieless, no IP storage, persistent cookie and click IDs opt-in.

Open design questions for Draft 0.3

  • Blocking: package/product name, Composer vendor/namespace and facade name — must not collide with Pennant (Feature), Spatie (Analytics) or Laravel (Context).
  • Monorepo split tooling (monorepo-builder vs. splitsh action) and whether all packages share one changelog.
  • Whether Laravel 11 support is worth the cost, given Filament 5 permits 11.28+.
  • Default inactivity timeout and hard cap for analytics sessions; whether campaign change mid-session starts a new session or a new touchpoint only.
  • Whether the client beacon ships in core or as its own package.
  • Default raw-event retention period and whether “forever” is allowed without an explicit opt-in warning.
  • Whether anonymous website tracking ships enabled or must be explicitly enabled.
  • Exact event-property query DSL for conversions/features/cohorts.
  • Whether the initial release includes native table partition management or leaves it to the host DBA.
  • Whether definitions are editable only in Filament or also via a framework-neutral API/UI contract.

Research Notes for This Draft

This draft deliberately follows current framework capabilities: Livewire 4 documents JavaScript action/message/request interceptors (client-side) and a PHP ComponentHook lifecycle (server-side) — this package uses the latter for facts; Filament 5 is released, requires Livewire 4, and supports a plugin ecosystem; Spatie's Laravel package skeleton/package-tools conventions remain a strong model for package structure. Timescale support is treated as capability-based because managed PostgreSQL providers can expose different subsets of Timescale functionality.

Draft 0.2 review sources: Livewire 4 lifecycle-hooks documentation; Filament 5 upgrade guide (PHP 8.2 / Laravel 11.28+ / Livewire 4 / Tailwind 4 floors); Laravel Context documentation; Pennant and spatie/laravel-analytics facade names.

Draft status: architecture-first. Names, exact migrations/indexes, query DSL grammar, and public API signatures should be finalized in the next design pass before implementation.
